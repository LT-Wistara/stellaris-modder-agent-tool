# Architecture and corpus findings

Pipeline: CWT bytes → trivia-preserving lexer → structural AST → complete internal symbol index → registry search/get + schema catalog/file-get + conservative validator → CLI / MCP.

## Registry / schema split (1.4)

All 173 documents remain parsed and indexed at startup. The 20 root CWT files serve
registry identifier lookup; 153 subdirectory files are schema catalog entries.
list_files returns only their sorted relative paths. get dispatches an existing
`.cwt` path to its cached Document.source, without field JSON or added metadata.
In 1.4.1 the same whole-file limit applies to root and subdirectory files: at most
800 lines are returned; larger files yield USE_SEARCH with an explicit size warning
and a file-scoped search instruction. Line counts use source.splitlines(), including
comments/blank lines without counting a trailing newline as an extra line. Caller
paths never cause filesystem reads; membership is checked in the loaded corpus.
Unknown paths return NOT_FOUND with a list instruction.

Public search eligibility is separate from the internal semantic index. Both exact
and template search, fuzzy candidate shortlisting, results and related exclude local
subdirectory fields. Root registries expose top-level declarations and immediate
entries of known registry containers, not their nested fields, parameters, enum
members or metadata. search_ids enforces this boundary before ranking/truncation;
registry_ids remains the detailed definition-lookup eligibility set. For example,
modify_species/base is private while alias[modifier_rule:base] remains searchable.
Direct get-by-id and Validator lookup keep all previously accessible nodes, aliases
and schema rules; parent get still includes complete parameter definitions.
Existing retrieval weights and scoring are retained to avoid recalibrating interface
fuzzy matching. Small schema type filters/ids produce USE_SCHEMA_FILE. For schemas
larger than 800 lines, an explicit file type enables internal-field search and get
by candidate name/type (or result id in CLI), so the size warning has a working fallback. Global search still
excludes these fields. This does not change validation or fuzzy scoring.

Corpus inspection found root helper schemas (mod/dlc descriptors), and local aliases
in subdirectory GUI/economic/graphics schemas. Local aliases stay private to schemas;
root helper definitions remain available individually. Explicit global
alias[trigger/effect/modifier:...] declarations would remain public if moved into a
subdirectory in a custom/future corpus; none occur there in the bundled snapshot.
Top-level registry containers such as modifiers/enums/scopes are not public symbols,
preventing their ids from becoming whole-registry shortcuts.

The advertised MCP tools are stellaris_search, stellaris_list(), stellaris_validate and
stellaris_doctor. Name search resolves the visible candidates through the same internal get
dispatcher and embeds their sliced declarations, so one MCP call replaces search-then-get.
When a Stellaris installation is detected the server
additionally indexes the game's own script files and the mod that contains the tool (see
docs/DYNAMIC_DATA.md): names declared or generated by that data resolve as CONFIRMED_GAME_DATA
instead of TEMPLATE_MATCH/UNKNOWN, and template placeholders are verified against real objects.
Without a detected installation the server is byte-for-byte the CWT-only release in behaviour,
and stellaris_doctor reports why. The prior stellaris_get(target,type?) and
stellaris_get_definition(name,type?) names remain callable compatibility aliases to the same
dispatcher, but are not advertised. Example: stellaris_list() → common/buildings.cwt →
stellaris_search(query="common/buildings.cwt") → complete building schema.

## Observed corpus

Pinned upstream commit `9d417d7ef783fd5198b35ae55675923f1cf24101` contains 173 `config/**/*.cwt` files and 23,057 AST nodes. Root files are included along with all nested directories. Statements include assignments, list values, anonymous blocks, quoted strings, nested bracket declarations and embedded angle references. Structural statement operators in this snapshot are `=` and `==`; semantic comment metadata also uses `<>`. Numeric interval types can mix delimiters, e.g. `int(0..inf]` and `float[0..1]`.

Observed declaration families include alias, alias_name, single_alias, type, subtype, enum, complex_enum, value, value_set, macro and typed numeric/path/scope forms. The grammar does not need a per-file regular expression for any of them. Every node, including enum members and metadata structures written as ordinary CWT blocks, has a stable source-location id. Repeated declarations are retained.

Only assigned enum blocks with children enter the static enum index; bare `enum[x]`
nodes inside schemas are references, not empty declarations. A `complex_enum[x]` maps its
CWT-declared source path and member path to the matching game/mod definition type, whose
real object blocks provide the values used by validation.

Comments include both structured `##` annotations and natural-language prose. Known annotation keys include cardinality, scopes, push_scope, replace_scopes, type_key_filter, modifier_categories, inject, event_type, display_name and others. `corpus` reports the inventory; definition results retain raw comments, parsed keys, operators and values. Annotation parse failures are represented explicitly as `__unparsed_metadata__`, never discarded. The release corpus has zero such failures.

## Lossless structure

Tokens store kind, complete spelling, byte-decoded character offsets and line number. Whitespace tokens preserve empty lines and original line endings. Strings preserve quotes and escapes; nodes expose decoded key/value text as well as quoted flags. A node has its operator, children, parent, document and exact source span. `Document.roundtrip()` concatenates tokens back to exactly the original text; corpus tests compare UTF-8 bytes.

Unknown structural syntax raises `ParseError` with source location. Unknown declaration names are valid generic atoms, remain indexed, and are not silently interpreted as a familiar game interface. Semantic incompleteness is not relabeled as a parser failure or as proven validity.

## Index and provenance

The database is constructed once per server process. Name lookup uses a dictionary; all source locations remain in result lists. canonical type is the config-relative file path without `.cwt`; trigger/effect aliases and entries directly beneath `modifiers` additionally receive semantic kinds. Type basename ambiguity is surfaced.

Literal matches are CONFIRMED_CWT evidence for the declaration itself. Partial candidates are SUGGESTION. Scope categories come exclusively from `modifier_categories` supported_scopes and are ordered unions, with sources for each category. Unresolved category names prevent a complete `resolved` string.

Alias source paragraphs are assembled from complete sibling AST nodes joined across gaps without blank lines. A blank line inside a nested block cannot truncate that block. Continuous leading documentation is included; this preserves v5's validated overload behavior without line-regex extraction.

## Template matching

Template structure is split into literal and placeholder segments. Full matches anchor all literals and constrain placeholder spelling/length. A naked type placeholder does not match arbitrary API names. Querying the template declaration itself is still a literal CWT match.

Full template evidence is unchanged. Fuzzy template alignment never contributes existence evidence. The 1.3 scorer replaces the earlier anchored-prefix heuristic: it walks the same literal/placeholder structure, accepts a genuine truncation of the final token, and grants a character-anchored bonus measured as the share of the query the template's own words spell out. Placeholder capture contributes no literal credit, and the four gates in the retrieval section above bound how much of a query one wildcard may absorb. No embeddings, network queries or generated symbols are used. Validator spelling suggestions remain unchanged and never rewrite input.

## Identifier retrieval (1.3)

`scoring.py` holds the whole relevance model as one pure function of a `MatchFacts`
record, so thresholds can be unit-tested and calibrated without running a query.
`retrieval.py` holds the indexes, the strategy union and the alignment; it only ranks
names that exist in the index and never supplies existence evidence.

Candidate generation is a union of five strategies that are never short-circuited:
exact token postings, token-typo postings over a character-bigram vocabulary, compound
token postings (both directions of a separator mistake), rare-token completion seeds,
and fixed-literal runs of dynamic templates. Short queries additionally get a plain
substring sweep that only ever reaches the browse tier. Every name is scored once and
then expanded to its real symbol locations, so overloads stay distinct rows.

Alignment is a weighted Damerau-style dynamic program over tokens that emits a full
edit script. Exact correspondence is free; substitutions are only allowed when the
corpus confirms them (exact token, curated typo within a bounded distance, or a
truncation that is a real prefix of a real token). Anything else must be paid for as a
dropped token, so a speculative reading can never become a cheap substitution.
Equal-cost alignments are broken toward real correspondence and, among dropped tokens,
toward the one the candidate does not contain, which is what makes the explanation read
`has_background_job + extra pop` rather than `+ extra has`.

The score is `100 * (align * (0.55 + 0.45 * support) + bonus)` capped at 98, where
`support` is the share of query tokens with real literal correspondence, `align` is the
normalised weighted edit cost with a floor on how far a short query may discount it,
and `bonus` is a bounded completion bonus preferring informative completions over
completions of ubiquitous tokens. Dynamic templates carry four additional gates:
fixed literals must cover half the candidate and 55% of the query mass, every
placeholder must bind for a rankable row, reached thresholds mean the template has to
be at least 75% explained, and a wildcard that swallows several query tokens must stay
smaller than the literal evidence. Those gates are what keeps
`country_resource_energy` at NOT_FOUND while `country_resource_max_energy_ad` still
completes.

`Database.search` runs CWT exact and template evidence first (they alone set
`CONFIRMED_CWT` and `TEMPLATE_MATCH` and always outrank suggestions), then merges the
ranked candidates. Rows at or above `MIN_SCORE` with enough support become `results`;
weaker rows that still share real tokens become the separate `related` browse list.
Scoring never changes `lookup`, `get_definition`, parser behaviour, scope resolution or
validator evidence.

A cheap one-sided bound (cheapest ordered assignment of query tokens to candidate
tokens, plus a greedy screen) skips names that cannot reach the browse tier before the
full scorer runs. It can only drop names the full scorer would also place below the
threshold, and a regression test asserts exactly that over the whole corpus.

The corpus-derived calibration, the cutoff sweep, the holdout results and the measured
before/after behaviour are in [FUZZY_SEARCH_REPORT.md](FUZZY_SEARCH_REPORT.md).

## Validation

The script is parsed structurally with the same parser. Rules derive from AST definitions, not per-object hardcoded field lists. Nested aliases, single aliases, generic injected fields, numeric/bool/enum rules and static scope transitions are followed. CWT `==` permits comparison operators; `=` is assignment-only. Template object keys retain TEMPLATE_MATCH evidence.

Each checked identifier has source provenance or an explicit unknown/unresolved finding. Unknown parent blocks mark children unresolved instead of treating them as valid or continuing with a guessed context. Dynamic game objects are not inferred from familiar names. Subtype-dependent fields, ambiguous block overloads, runtime references and unimplemented constraints remain unresolved. The coverage object states what is and is not checked; this is not a replacement for CWTools or the Stellaris engine.

A bare context string keeps type semantics for trigger/effect/modifier and resolvable CWT
paths. If it is instead a known root schema with no type/path interpretation, it is accepted
as shorthand for `{schema: name}`. This preserves existing callers while making
`context="scripted_effect"` agree with the spelling accepted by search.

## Transports

Four coarse tools serve declaration/text/file search, catalog list, validation and environment diagnostics. stdio uses newline-delimited JSON-RPC and emits operational messages only on stderr. Streamable HTTP is stateless, supports JSON responses and 202 notification acknowledgements plus an optional keep-alive SSE stream. Both transports reuse one Database. Each validation call owns its diagnostics, so HTTP requests do not share mutable validation state.

Text search performs a bounded full scan in parent-directory round-robin order, then ranks
matched directories/files by hit density and interleaves their rows. It reports `returned`,
`has_more` and `scan_complete`; an exact `total` exists only for a completed scan, while an
incomplete scan reports `matched_at_least`. The legacy `truncated` boolean remains for older
clients but no longer masquerades a one-row probe as a total.

Detailed Database/Validator results and CLI retain per-result provenance, semantic fields, a compact dataset commit and shared-source definition_ref. The full upstream manifest is restricted to stats/corpus and the bundled manifest file.

Both MCP transports apply the pure whitelist in projection.py at Server.dispatch, without mutating detailed results or changing retrieval/validation. Every tool has exactly one compact output shape; no tool takes a `detail` argument, and one passed by an already-configured client is accepted and ignored. Search returns name/type per row, split into evidence, templates and suggestions, and signals truncation; it carries no status, score or kind. Get returns status/type/full CWT text per source group, resolving references internally, and emits no per-entry `source`. Modifier scopes and unresolved category reasons remain explicit. Validation preserves aggregate status and counts, omits routine confirmed findings and source metadata, and retains actionable/uncertain findings including templates, expected values, scopes and suggestions. Early errors retain context choices and reasons. File/list responses remain minimal. MCP serializes the compact projection once as JSON in `content[0].text` and does not return `structuredContent`, so clients that expose only the standard text channel retain the complete projected result. CLI remains the route to detailed diagnostics.

All runtime dependencies are in Python's standard library. Source-path data lookup is independent of process working directory. Optional packaging metadata supports installation, but neither installation nor an external build backend is needed to run the extracted distribution.
