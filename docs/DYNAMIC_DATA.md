# Game and mod data (dynamic names)

The server reads these data sources when available:

1. **the Stellaris installation** — the game's own script files;
2. **every manually configured Mod directory** — the source folders added by the user.

The launcher database, playsets and other installed mods are deliberately *not*
read: indexing uses vanilla plus only the folders the user selects.

Everything is read-only. If neither a game installation nor a Mod directory is available,
the server uses only the bundled CWT corpus. `stellaris_doctor` reports the available sources.

## Choosing data sources

`stellaris_doctor` reports every step it tried. Detection order, first hit wins:

1. `--game-root` argument (or `STELLARIS_GAME_ROOT`);
2. the Steam installation from the Windows registry (`HKCU\Software\Valve\Steam`,
   `HKLM\SOFTWARE\WOW6432Node\Valve\Steam`);
3. every Steam library listed in `steamapps/libraryfolders.vdf`
   (`appmanifest_281990.acf` confirms the app);
4. the usual install locations per platform.

A game candidate is accepted only when it contains the game executable, `common/defines/00_defines.txt`
and `common/economic_categories/`. Mod roots are never inferred from the tool's location.
Add them in the GUI, repeat `--mod-root`, or set `STELLARIS_MOD_ROOT` for one directory. Without these,
Mod scripts are not indexed. An explicit path remains usable even without `descriptor.mod`.

```bash
python stellaris_modder_tool.py doctor                 # what was detected, and what was indexed
python stellaris_modder_tool.py --game-root "D:/Games/Stellaris" search has_background_job
python stellaris_modder_tool.py --mod-root "D:/MyMod" doctor
python stellaris_modder_tool.py --mod-root "D:/MyMod" --mod-root "D:/OtherMod" doctor
python stellaris_modder_tool.py --no-game-data stats   # pure CWT: never touches disk outside the tool
```

## What is indexed

The bundled corpus already declares *where* every definition type lives (`type[x]` with
`path` / `path_extension` / `name_field`). Only those directories are scanned, from the
game first and then from each configured Mod in order. Later folders win on conflicts. That is a few dozen files
instead of the whole game tree.

Only the members consumers need are kept (for example the economic-category declaration
members); definition text is sliced from disk on demand. The scan is lazy — it happens on
first use, or at startup for the MCP server — and costs a few seconds.

## How names resolve

| Name | Evidence |
| --- | --- |
| declared in the corpus | `CONFIRMED_CWT` |
| declared or generated by game/mod data | `CONFIRMED_GAME_DATA` |
| matches a documented template shape | `TEMPLATE_MATCH` |
| nothing matches | `UNKNOWN` |

Three kinds of dynamic name are handled:

1. **Template modifiers** (`job_<job>_add`). Each placeholder is verified against the
   indexed definitions, so `job_researcher_add` is confirmed only when `researcher` really
   is a job; a name that only *looks* right is reported `UNKNOWN` instead.
2. **Economic-category modifiers** (`planet_jobs_energy_produces_mult`). These are not
   written anywhere: the game generates them from `common/economic_categories`. They are
   reproduced from the real declarations (`modifier_category`, `generate_add_modifiers`,
   `generate_mult_modifiers`, `triggered_*`), the `resource` definitions and the
   `economic_modifier_category` / `economic_modifier_type` enums, including the rule that
   resource-less names exist only for `_mult`. Supported scopes come from the modifier
   category, falling back to `economic_unit`.
3. **Mod declarations** (scripted triggers/effects and other definition types). These are
   indexed from the mod and resolve to their file and line, so identifiers the corpus cannot
   know are no longer reported `UNKNOWN`.

Literal object references in validation use the same definitions. Types already needed by
templates reuse the startup index; broader references such as `<technology>` are scanned by
their CWT-declared directory on first use and cached. A real name becomes
`OBJECT_REFERENCE`; an absent literal becomes `UNKNOWN_OBJECT_REFERENCE`, with close names
when available. Runtime expressions and incompletely scanned types remain `UNRESOLVED`.

Existence is claimed; structure is not. The *body* of a mod-declared trigger or effect is
not validated against the CWT declaration yet. Complex enums whose CWT declaration names a
definition path are harvested from the loaded definitions: for example `section_slot`
comes from each real `ship_size.section_slots` block, including mod-added slot names. If the
required definition scan is unavailable or incomplete, the value remains `UNVERIFIED`
rather than being guessed or falsely rejected.

## Literal text search

Text mode inventories the allowed game/mod script directories, scans files round-robin by
parent directory, and ranks matched directories/files with a density-aware score before
round-robin output. Alphabetically early folders therefore cannot consume the result limit.
`returned` is the number of rows in the response and `has_more` means confirmed matches were
omitted. `total` is present only after a complete scan; a bounded/incomplete scan reports
`scan_complete: false` and `matched_at_least` instead, so a probe count is never presented as
the real number of occurrences.

## Fuzzy search covers both sources

A name guessed from memory is usually slightly wrong, so the typo-tolerant retrieval index
is rebuilt once to include the game/mod names as well: a query like `planet_jobs_energy_produces_mul`
or a half-remembered own trigger name resolves to candidates instead of nothing. The rebuild
costs about half a second and raises the indexed name count from ~13k to ~30k on vanilla 4.6;
it happens lazily, only when game/mod data is actually loaded, and it never turns a fuzzy
candidate into evidence — those rows stay `SUGGESTION`.

## Freshness: new entries appear without a restart

Modding is iterative, so a long-running server must not keep answering from a stale
snapshot. The scanned definition directories are fingerprinted as `(file count, total
bytes, mtime sum)`; a change there rebuilds the index (and the fuzzy name index with
it). The check is a directory walk -- about 4 ms for a vanilla install -- and is
throttled to once every two seconds, so a burst of requests pays it at most once.

* a **new file** changes the file count, so it is noticed immediately;
* an **edit** changes the timestamp sum even when the file keeps its size (a maximum
  timestamp would miss edits to any file that is not the newest one);
* a **deletion** changes both count and sum.

`--no-watch` (or `STELLARIS_WATCH=0`) switches it off, which is what a hosted server
with a frozen data upload wants. `stellaris_doctor` reports
`watch: {enabled, interval_seconds, rebuilds}` so freshness is observable.

## Notes for a hosted deployment

Path detection is inherently machine-local. A server running where the game is not
installed will report `enabled: false` with a reason and stay CWT-only — that is expected,
not a failure. Point it at a game directory explicitly when the process cannot see the
user's disk, or run it on the machine that has the game.
